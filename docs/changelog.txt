WHAM-XREX-PFMG474 Firmware Changelog
=====================================

2026-09-17  —  XREX pin relabeling + real per-channel Water/Temp/
               Enerpro/OCP fault detection (xrex_io.c, new module);
               NORMALLY_HIGH polarity override; XREX:CHANnel:STATus?
-----------------------------------------------------------------------
  Change:  User added a new "XREX Pin Name" column to docs/
        pin_mapping_v4.csv, naming a variety of pins on this Transrex
        controller by role: XR1-XR4 are Transrex 1-4, each with its own
        _WATER_FLT/_TMP_FLT/_ENERPRO_FLT/_OCP_FLT (fault inputs),
        _FEEDBACK/_DRIVE (relabels of the existing PFM_Input_01..04 and
        HRTIM1_CH* pins, zero functional change), and _ENA_OUT/
        _CONTACT_OUT (new outputs, explicitly DEFERRED -- see below).
        Extracted the full mapping PROGRAMMATICALLY (a Python
        csv.DictReader script, not by eye), given the safety stakes and
        this project's established pattern of catching pin-mapping
        mismatches early (PC14-vs-PF15, PF13-vs-PD1, both 2026-09-16).

        Requested behavior: Water/Temp/Enerpro count as "General Fault"
        (SM_FAULT_GENERAL); OCP is its own fault type
        (SM_FAULT_OVERCURRENT); each fault category independently
        polarity-configurable, defaulting NORMALLY_HIGH; and -- the
        core new behavior -- a channel's own fault pins only count
        toward a fault when that Transrex channel is actually enabled
        (PID_GetChannelEnable()), so e.g. running XR1 alone never
        blocks/stops output because XR2/3/4's fault pins read LOW.

        POLARITY CONFLICT, resolved by direct user confirmation: the
        existing GDS_FAULT_POLARITY = GDS_NORMALLY_LOW (ctrlr_config.h)
        had been set 2026-09-08 from a real hardware snapshot of these
        SAME 12 physical pins (11/12 LOW, 1 HIGH, consistent with
        LOW=healthy). The user's new instruction requires the OPPOSITE
        -- NORMALLY_HIGH -- for Water/Temp/Enerpro. Confirmed directly
        ("During normal non-faulted operation, these pins will be
        normally high... falling edge registers as a fault") as a
        deliberate override, not a mistake, and implemented as such,
        with the contradiction documented in ctrlr_config.h. NOT yet
        independently re-verified against a real healthy (non-floating)
        signal on these pins -- flagged open below.

        EXTI HARDWARE CONFLICT, found before implementation, not after:
        initial plan was EXTI-interrupt-driven OCP detection (user's
        own first choice, on my recommendation). Before writing any
        code, mapped the 4 new OCP pins (PF4/PF5/PF8/PF12) to their EXTI
        line numbers and found PF4(EXTI4)/PF5(EXTI5)/PF8(EXTI8) directly
        conflict with PE4/PE5/PE8 -- already claimed by the existing
        GateDriverStatus EXTI setup (STM32's 16 EXTI lines are shared
        project-wide, one GPIO port per line via SYSCFG_EXTICR); only
        PF12(EXTI12, XR3_OCP) was actually free. Flagged this as a real
        hardware constraint, not a preference; user agreed to poll all
        4 OCP pins uniformly instead of mixing 3-polled-1-EXTI.

        New module Core/Src/xrex_io.c + Core/Inc/xrex_io.h -- owns all
        new XREX-semantic fault interpretation, sitting ON TOP of
        gate_driver.c's existing raw GateDriver_Read() accessor for
        Water/Temp/Enerpro (reused, not duplicated) and owning entirely
        new OCP polling (no prior code existed for this).
        gate_driver.c's own naming/identity/GDS?/GateDriver_* functions
        deliberately left UNCHANGED (per direct labeling-scope decision
        -- "add a secondary label for querying, then document and new
        code" -- the GDS/GateDriverStatus language stays as-is, it was
        chosen for the sibling limiter/HVPS h-bridge supplies project
        and is simply outdated terminology here, not wrong code); only
        GateDriver_CheckFault()'s internal fault-DECISION logic now
        delegates to XrexIo_EvaluateGateDriverFault().

        New XrexIo_PollOcpFaults() called every PID_Update() tick and
        once at boot, alongside the existing SM_PollFaults() call --
        reads PF4/PF5/PF8/PF12 directly (GPIO_PULLDOWN, matching this
        project's established fail-safe-default convention) and calls
        the pre-existing SM_ReportOcpFault(channel) (originally added
        for OCP:TEST:FAULT software injection) on a real fault.

        New XREX:CHANnel:STATus? <ch> (commands.c/.h, cmd_parser.c) --
        per-channel WATER/TMP/ENERPRO/OCP readback by name, backed by
        new XrexIo_GetChannelStatus(). Reuses ERR 11/12 (invalid/
        missing channel), matching every other numbered-channel
        command's convention -- no new error codes needed.

        BUILD GOTCHA hit and fixed (matches AGENTS.md's own documented

2026-09-16  —  External trigger added (rising edge on PF15 fires a shot
               while ARMED); PID:LOOPMODE now accepts ch=0 for "every
               channel" -- NOT YET VERIFIED ON REAL HARDWARE, board
               still unavailable
-----------------------------------------------------------------------
  Change:  Direct follow-up request, same session as the external-enable
        interlock just below: expand PF15's role so a rising edge, while
        ARMED, fires a shot -- "the same behavior as running
        PID:PROF:STAR when in closed loop operation, or our open loop
        start call when in open loop operation. Closed vs open loop
        should be set by SCPI command."

        Real clarification needed and resolved before writing any code:
        asked directly whether "our open loop start call" meant the
        legacy pfm.c TABLE:*/FIRE path (the only genuinely open-loop,
        zero-PID-involvement mechanism in this codebase), or something
        that didn't exist yet and would need building. User's answer
        revealed the real architecture: open- vs. closed-loop has
        ALWAYS been the per-channel PID:LOOPMODE flag, checked inside
        the SAME PID_Update() loop both PID:START and
        PID:PROFile:STARt already share -- there was never a second,
        structurally-different "open-loop start call" to invoke. Once
        that was clear, confirmed the design directly: the trigger
        always calls SM_Fire() (PID:PROFile:STARt's own function, the
        state-machine-gated path, not the ungated PID:START), and the
        "closed vs open loop, set by SCPI command" request becomes a
        plain convenience for setting every channel's PID:LOOPMODE at
        once, not a second code path the trigger branches on.

        PID:LOOPMODE (cmd_pid_loopmode(), commands.c): `ch=0` now means
        "every channel at once" -- reuses PID:LOG's own existing
        `ch=0`-means-all convention (added 2026-09-10, PID_ArmLogAll())
        rather than inventing a new command. Real channels are still
        1..HRTIM_NUM_CHANNELS as always.

        External trigger itself (state_machine.h/.c): reuses PF15, the
        SAME pin the external-enable interlock (below) already uses --
        not a second signal. Structurally DEPENDS on external-enable
        being on: SM_SetExternalTriggerRequired(1) refuses (new ERR 16)
        unless SM_GetExternalEnableRequired() is already 1, and turning
        external-enable back OFF forces trigger back off too --
        enforced both directions so an operator can never end up with
        triggering active while the "lose the signal -> fault"
        protection it depends on is silently disabled. Per direct
        instruction ("as usual, if we lose the enable signal we should
        interpret this as a general fault"), this is the EXISTING
        SM_FAULT_EXTERNAL_ENABLE mechanism (previous entry), reused
        as-is -- no second fault path.

        Edge detection, not level detection: a baseline PF15 level is
        captured fresh the instant SM_Arm() succeeds (so a signal
        already HIGH at the moment of arming doesn't look like a rising
        edge on the next check), then kept current by SM_PollFaults()
        on every call while still ARMED. Checked from INSIDE
        SM_PollFaults() itself (not a new, separate poll function) --
        shares that function's already-established call-site guarantee
        (main loop + every real PID_Update() tick) rather than adding a
        second entry point every caller would need to remember. While
        merely ARMED (not yet FIRING), the only caller actually reaching
        SM_PollFaults() is the main loop -- its own iteration rate is
        unbounded/undocumented (the SAME pre-existing "NOTE TO REVISIT"
        this project already carries for fault-poll cadence), so
        trigger latency while ARMED inherits that same limitation, not
        a new one. If the resulting SM_Fire() call itself fails (e.g.
        profile timing never set), the state simply stays ARMED with
        the baseline now recording HIGH -- a genuine falling-then-rising
        edge is needed to retry, not just PF15 remaining HIGH.

        New wire commands (commands.c/.h, cmd_parser.c): EXTernal:TRIGger
        <0|1>, EXTernal:TRIGger?. New ERR 16 (EXTernal:TRIGger refused,
        EXTernal:ENAble must be on first).

2026-09-16  —  External-enable interlock added (PF15, "Fiber_Enable"):
               new SM_FAULT_EXTERNAL_ENABLE fault type, EXTernal:ENAble
               commands -- NOT YET VERIFIED ON REAL HARDWARE, board
               unavailable this session
-----------------------------------------------------------------------
  Change:  Direct request: a config parameter to "set external enable
        true"/"set external enable false" on pin PC14 -- when true, the
        controller should refuse to output a shot unless that pin reads
        HIGH, and should register a fault if the signal is lost during
        a shot.

        Pin correction BEFORE any code was written: PC14 is documented
        in docs/pin_mapping_v4.csv as "STM_Enable_Pin", direction GPO
        (General Purpose Output) -- the STM32 DRIVES that pin outward
        per the schematic, the opposite direction needed for a signal
        the controller is supposed to READ. Flagged directly rather
        than silently reconfiguring a documented output pin as an
        input; user confirmed the real intended pin is PF15
        ("Fiber_Enable"), which IS documented GPI (input) in the same
        CSV -- the correct pin for this purpose.

        Implementation, in state_machine.c/.h (this project's existing
        top-level IDLE/ARMED/FIRING/FAULT machine -- the natural home,
        since this interlock directly gates ARM/FIRE and is itself a
        new fault source, exactly the two things that module already
        owns):
          - New SM_FAULT_EXTERNAL_ENABLE fault type -- system-wide, like
            SM_FAULT_GENERAL, and reuses its exact ramp-down response
            (HandleGeneralFault() called directly) -- reported as its
            own distinct type purely for operator diagnostics (STATE?
            -> "OK FAULT EXTERNAL_ENABLE"), not a different physical
            response.
          - ArmConditionsMet() (previously a pure stub, always returning
            1 -- see the 2026-09-13 entry) now has its FIRST real
            condition: refuses ARM unless the interlock is off, or on
            AND PF15 reads HIGH.
          - SM_Fire() (the ARMED -> FIRING transition, PID:PROFile:STARt)
            ALSO re-checks the interlock immediately before firing --
            closes a real gap where PF15 could drop in the window
            between a successful ARM and the eventual START; ARM alone
            does not guarantee the condition still holds at the actual
            moment of firing. cmd_pid_profile_start() (commands.c)
            checks this itself first, for a precise ERR 15, rather than
            relying on SM_Fire()'s own generic failure return --
            matching that function's existing "distinct failure
            reasons, reported distinctly" precedent for the
            PID:PROFILE:TIMING-not-set case.
          - SM_PollFaults() checks PF15 continuously, but ONLY while
            SM_STATE_FIRING -- per direct instruction ("if that input
            is lost during a shot"), NOT while merely IDLE/ARMED
            (nothing outputting yet to protect there; the next
            PID:PROFile:STARt attempt simply fails its own re-check
            instead). Whether ARMED should also actively fault on loss
            was NOT decided either way -- not asked for, flagged rather
            than silently added.
          - SM_ClearFault() re-validates PF15 is back HIGH before
            actually clearing an EXTERNAL_ENABLE fault, same "only
            clear if the condition is actually gone" treatment
            PC10/GateDriverStatus already get (see the 2026-09-15
            entry on that same philosophy).

        GPIO config: main.c's MX_GPIO_Init() (matching gate_driver.c's
        own established precedent -- plain-input GPIO config lives in
        main.c, the read/fault logic lives in the owning module, not a
        new hand-rolled Msp-init pattern). PF15 is GPIO_PULLDOWN, NOT
        this project's usual GPIO_NOPULL for actively-driven inputs
        (GateDriverStatus, PFM_Input, QUADSPI) -- a DELIBERATE fail-safe
        choice specific to this one signal: an unconnected/floating
        PF15 must read LOW (no permission granted), never an undefined
        level that could accidentally read HIGH and silently permit
        firing. GateDriverStatus's own NOPULL is fine on its pins
        because floating-reads-as-fault is already the safe direction
        there; the same reasoning would be UNSAFE here, where
        floating-reads-as-enabled would be the dangerous direction
        instead. Plain polled input, no EXTI -- SM_PollFaults()'s own
        existing cadence (main loop + every real PID_Update() tick,
        ~1kHz while FIRING) was judged sufficient; an interrupt-driven
        path was considered and not built, flagged as a real decision
        to revisit if tighter latency ever matters, not silently
        assumed already covered.

        New wire commands (commands.c/.h, cmd_parser.c): EXTernal:ENAble
        <0|1>, EXTernal:ENAble?, EXTernal:INPut? (raw PF15 level,
        independent of whether the interlock is on -- same diagnostic
        role PFMIN:DEBUG:RAW?/REG? played for the fiber-patching
        investigation, previous entry). Two ':'-levels (not one
        compound "EXTEnable" token) specifically so "ENAble"/"INPut"
        each get their own independent SCPI short-form abbreviation
        (EXT:ENA / EXT:INP) -- a single compound word would only let
        the unrecognizable fragment "EXTE" be typed as a short form,
        since this project's scpi_token_match() only recognizes a
        LEADING uppercase run, not capitals resuming mid-word. New
        ERR 15 (PID:PROFile:STARt refused, interlock on + PF15 LOW).
        STATE? extended for the new fault type.

  Verify: clean arm-none-eabi-gcc build, zero warnings. *** NOT YET
        VERIFIED ON REAL HARDWARE *** -- the board's USB-serial adapter

2026-09-13  —  Fixed a real race condition in SM_PollFaults() that could
               silently replace a General-Fault ramp-down with an abrupt
               cutoff (build verified; real-hardware verification PENDING
               -- board still disconnected)
-----------------------------------------------------------------------
  Change:  The previous entry (General Fault ramp-down, below) noted in
        passing that g_state (state_machine.c) is read/written from BOTH
        main.c's main loop and PID_Update() (HRTIM1_Master_IRQn, priority
        1, which can preempt the main loop at any instruction), and that
        a narrow window existed where the main loop could read g_state
        (not yet FAULT), get preempted by the ISR's own SM_PollFaults()
        call completing EnterFault() first (possibly starting a General-
        Fault ramp-down), and then resume and -- since its own check had
        already passed, before preemption -- call EnterFault() a second,
        redundant time. That second call would see g_stateBeforeFault ==
        SM_STATE_FAULT (not SM_STATE_FIRING, since the first legitimate
        call had already transitioned it) and take HandleGeneralFault()'s
        "else" branch, calling PID_Stop() immediately and silently
        replacing the just-started graceful ramp-down with an instant
        cutoff.

        That entry characterized this as "SAFETY-NEUTRAL... not a
        hazard," on the reasoning that the physical end state ("output
        off") was the same either way. Directly corrected: "This worst
        case is actually quite bad -- we need to guarantee smooth
        behavior in this fault case." Right call -- the whole point of
        specifying a linear ramp instead of an instant stop was to avoid
        inductive/mechanical stress on the magnet and supply; a race that
        silently substitutes the abrupt path for the graceful one IS the
        hazard the ramp-down was built to prevent, not a neutral outcome.
        Documenting a known safety-relevant race instead of fixing it was
        the wrong call, and it's fixed properly now, not just described.

  Fix:  SM_PollFaults() (state_machine.c) now wraps its entire read-
        check-transition sequence -- the "already FAULT?" check, both
        fault-source reads, and the EnterFault() call itself if triggered
        -- in __disable_irq()/__enable_irq(), this codebase's own already-
        established critical-section pattern (see boot_jump.c's VTOR/
        bootloader-jump sequence, and main.c). Whichever context (main
        loop or ISR) reaches SM_PollFaults() first now runs the entire
        function to completion before the other context's own call can
        even read g_state -- the double-entry race is now structurally
        impossible, not merely low-probability. EnterFault()'s own work
        (PFM_ForceStop(), the fault-type dispatch, PID_BeginFaultRamp-
        Down()) is all fast, non-blocking register/flag writes with no
        dependency on any interrupt firing to complete, so it's safe to
        run with IRQs globally disabled. Calling this from inside an ISR
        (the PID_Update() call site) is fine too -- __disable_irq() while
        already inside an ISR is idempotent for the brief window this
        takes, matching how boot_jump.c already calls it unconditionally
        without special-casing ISR vs. main context.

        state_machine.h's "NOTE TO REVISIT" comment on this race has been
        rewritten to describe the fix rather than the (now stale, and
        wrong) "safety-neutral, not fixed this round" characterization.

  Verify:  Build-verified clean (zero warnings). Real-hardware
        verification is still pending (board disconnected this session)

        merely probabilistically rare.

2026-09-11  —  REAL BUG FIXED: GateDriverStatus fault during closed-
               loop PID operation left an operator with no way to

-----------------------------------------------------------------------
  Change:  Found while explaining this project's fault-handling
        architecture to the user, then fixed on direct request. Two
        independent fault sources exist: PC10/HRTIM1_FLT6 (real
        hardware fault input, autonomous in silicon) and
        GateDriverStatus_01..12 (software/EXTI-driven, gate_driver.c).
        PID_Update() already polled HRTIM1_FaultIsTripped() every tick
        and correctly called PID_Stop() when tripped -- but never
        checked GateDriver_FaultIsLatched() at all. GateDriver_
        CheckFault()'s PFM_ForceStop() (pfm.c) predates the PID
        architecture (2026-09-09) and was never integrated with it: it
        stops HRTIM output directly (including the Master counter, so
        PID_Update() genuinely stops being invoked), but with nothing
        checking the GateDriverStatus latch inside PID_Update() itself,
        g_running was NEVER cleared by this fault source.

        CONFIRMED impact, not just theoretical: PID_IsRunning()/
        PID:STATus? kept reporting running=1 after a GateDriverStatus
        fault, even with hardware output already genuinely stopped.
        Far more serious: PID_Start()'s own idempotency check
        (`if (g_running != 0U) return 1U;`) then silently turned every
        subsequent PID:START into a no-op -- no reconnect, no
        restarted feedback capture, nothing, and no error reported
        either (a plain "OK" comes back, indistinguishable from a
        real, successful start). FAULT:CLEAR didn't help -- it only
        ever cleared the two hardware/EXTI latches
        (HRTIM1_FaultClear()/GateDriver_FaultClear()), never touched
        g_running. Net effect: an operator had NO way to resume
        closed-loop operation after a GateDriverStatus fault short of
        a full reboot -- silently, with no error message pointing at
        why PID:START "succeeded" but nothing actually happened.

        Fixed with the minimal, already-proven mechanism -- extended
        PID_Update()'s existing fault check
        (`if (HRTIM1_FaultIsTripped() ...)`) to also check
        `GateDriver_FaultIsLatched()`, calling the same real
        PID_Stop() either way. No new recovery path designed or
        needed: this is the exact same bookkeeping (stop the Master
        counter so the ISR doesn't spin forever under already-safed
        outputs, clear g_running so IsRunning()/a later PID_Start()
        both see truthful state) the PC10 path already did correctly
        -- the GateDriverStatus source was just never plugged into it.
        pid.c now includes gate_driver.h.

        Build verified: clean rebuild, zero warnings. REAL-HARDWARE

        UNCONDITIONALLY -- open-loop and closed-loop alike, whether
        the desired value came from PID math, a plain PID_SetSetpoint()

        apply regardless of which code path computed the number. Sits

        existing directional anti-windup check (2026-09-09) needed no

        slew-clamping (or both) caused the difference.

        code: PID_Start() used to reset lastOutputHz to 0 -- an
        artificial value 0 was never actually a real, physically-
        achievable output (the hardware floor is PID_OUTPUT_MIN_HZ,
        3000 Hz), so the very first tick after every PID_Start() would
        have had the slew clamp count a fake, oversized "jump" from a
        starting point that never really existed, needlessly slowing
        the first real response. Now initializes to PID_OUTPUT_MIN_HZ.

        the whole point of a HARD clamp (per direct instruction): it

        than first trying to correctly classify every possible bad
        sample. Outlier-rejecting PfmInput_ConsumeAveragePeriod()'s
        result before it reaches PID math (the other option raised in
        the previous entry) remains a reasonable COMPLEMENTARY future

2026-09-10  —  Windowed-average feedback + real production shot

               open/closed-loop mode, CONFIRMED on real hardware
-----------------------------------------------------------------------
  Change:  Replaces the single-latest-sample feedback and the ad hoc
        static-setpoint/PID:RAMP-only demand of 2026-09-09 with the
        real production architecture, fully specified across a design
        discussion before any code was written (see this project's own

            averaging) over everything captured since the last
            consume, then resets the accumulator ("reciprocal
            frequency counting", standard practice for this kind of
            feedback). The averaging window's boundary is NOT synced
            to the Master heartbeat exactly -- doesn't need to be, per
            direct instruction, since the goal is a solid measurement
            of actual supply output, not exact period alignment.
            Lock-free by construction, not by an added critical
            section: HRTIM1_Master_IRQn (priority 1) can always
            preempt the DMA capture ISR (priority 3) but never the
            reverse, so a read+reset from Master's context can never
            race a concurrent accumulate from the DMA ISR.

            placeholder pending bench characterization) /

            nominal) -- the Amps<->Hz calibration layer, nested inside
            the existing hardware-register safety clamp
            (PID_OUTPUT_MIN_HZ/MAX_HZ, 3000/150000). Below
            PFM_TURNON_FREQ_HZ the Transrex supply outputs 0A; above
            PFM_MAX_FREQ_HZ its output saturates around
            PFM_MAX_CURRENT_A.

          - Core/Inc/pid.h, Core/Src/pid.c: the real shot-profile
            engine.
              * TrapezoidalCurrentA(elapsedTicks, demandCurrentA):
                0A -> linear up-ramp -> demandCurrentA -> flat-top ->
                linear down-ramp -> 0A, computed ON THE FLY once per
                Master heartbeat from a compact {rampTicks,
                flatTopTicks, demandCurrentA} state -- NOT a stored
                per-period table (not enough RAM for one, per direct
                instruction; this is the entire reason the profile is
                parametric rather than tabulated).
              * AmpsToHz(currentA): LINEAR PLACEHOLDER mapping
                [0, PFM_MAX_CURRENT_A] -> [PFM_TURNON_FREQ_HZ,
                PFM_MAX_FREQ_HZ], with 0A landing EXACTLY on
                PFM_TURNON_FREQ_HZ (no "off but nonzero" output state
                between 0A and turn-on), per direct instruction. Real
                Transrex SCR/phase-controlled-rectifier physics may
                not be linear (a cosine-like relationship between
                firing angle and output current is a real possibility)
                -- flagged in both ctrlr_config.h and pid.c as
                provisional, explicitly deferred to post-hardware-
                characterization, not silently assumed correct.
              * ONE shared/synchronized shot clock (g_profileElapsedTicks
                et al.), not one per channel -- per direct instruction,
                every channel's ramp/flat-top/ramp shape must stay
                perfectly synchronized in time even though each
                channel has its own peak demandCurrentA. Checked for
                completion BEFORE any channel is touched each tick.
              * PID_SetProfileTiming(rampTimeMs, flatTopTimeMs) /

        Architecture, as designed in conversation (not yet implemented):

          - NO shared PFM_Step_t table for this mode. Each of the 4
            channels is an independent {setpoint, PID state (Kp/Ki/Kd,
            integral accumulator), feedback source, output timer} tuple
            -- there is no pre-computed trajectory to walk, every output
            value is computed live.

          - Master-repetition interrupt (HRTIM1_Master_IRQn) is KEPT,
            deliberately, as a FIXED-RATE heartbeat -- this was
            explicitly reconsidered mid-design and is worth not
            re-litigating without rereading this entry. The first-draft
            idea (each channel's own roll-over triggers ITS OWN PID
            recompute, fully self-clocked, no Master involvement) was
            rejected: it ties each channel's control-loop sample
            interval to that channel's own instantaneous carrier
            frequency, which is itself what the PID is adjusting --
            variable sample-time PID is materially harder to tune/
            guarantee-stable than fixed sample-time PID, and conflates
            "how fast the V-to-F encoding happens to cycle" with "how
            fast the control loop should run" (the latter should track
            the Transrex/magnet's own electrical time constant, which
            has nothing to do with the demand signal's encoding rate).
            Master's role in Possibility 3 was never really "step a
            shared table" (that's just what the reference document's
            own example was doing with it) -- its real, general role is
            "a fixed-cadence, always-safe moment to WRITE shadow
            registers," which is exactly what a fixed-rate PID heartbeat
            needs, and keeping it doesn't reintroduce any of the mid-
            cycle hazard Possibilities 1/2 had, because the actual
            hardware APPLY still happens at each channel's own
            roll-over, per Possibility 3, regardless of what wrote the
            shadow or when.

          - Per Master tick, loop over the 4 channels: read PFM_Input's
            LATEST captured period for that channel's feedback (a new,
            simpler capture mode than today's PFMIN:CAPTURE <M>/STATus?/
            DATA? -- free-running, no target count, "give me whatever
            you last measured" rather than "capture exactly M periods,
            then stop"), convert period -> frequency (a real division,
            not optional -- PID error must be linear in frequency, since
            that's what's linear in the V-to-F encoding; period is not
            linear in the encoded value), run that channel's PID with a
            FIXED, known Delta-t (= the Master period), clamp, write the
            new PER into that channel's shadow register. CMP is very
            likely fixed/constant per channel (single-ended V/F tone,
            not a variable-duty PWM leg) -- simplifies away most of the
            PER/CMP-coherency hazard the reference document flags for
            the general case.

          - Master's own rate is a free, deliberately-chosen parameter
            now representing CONTROL BANDWIDTH, not carrier rate --
            expected to land far below the ~100 kHz carrier ceiling
            (tens of Hz to low kHz, matching real magnet-supply loop
            dynamics), which is what makes it safe to run 4x PID compute
            inside one interrupt without threatening PFM_Input's DMA
            margins (same headroom analysis as the priority-inversion
            fix below, ~8 periods/~80-160us before circular-buffer
            wraparound) -- should be validated empirically with
            PFM_GetDiagGapLog() (pfm.c, PFM:GAPLOG?) once implemented,
            not just assumed safe from the arithmetic alone.

        Explicitly NOT yet resolved (real open items, not implementation

          - Exact HRTIM per-timer IRQn lines are NOT needed for this

  Change:  Found while stress-testing the DMA-based PFM_Input capture
        below with progressively less trivial waveforms (an extreme
        zigzag, then a slower ramp/hold(100 periods)/ramp profile). The
        ramp/hold/ramp shot's real HRTIM output was confirmed, via a
        DSLogic ground-truth capture (all 6 channels agreeing, U vs UN
        median error 0.0), to genuinely stall on the wire: it holds one
        frequency for ~187 real periods instead of the table's
        programmed 100, then cleanly resumes the correct sequence ~77
        periods late. PFM:DIAG?'s existing single max-gap diagnostic
        (added the same day for a different, now-closed dead end) could
        not distinguish "one big stall" from "many small repeated
        delays," so a new diagnostic was added: PFM_GetDiagGapLog()
        (pfm.c/pfm.h) logs the raw DWT-cycle gap between every single
        PFM_CycleBoundaryHandler() call for the current shot (up to
        PFM_INPUT_MAX_PERIODS of them), exposed over serial as
        PFM:GAPLOG? (commands.c/commands.h/cmd_parser.c) -- TEMPORARY,
        same debug-command convention as PFMIN:DMASTAT?, meant to be
        removed once this investigation closed.

        The raw gap log immediately showed the real mechanism: not one
        stall, but a spike of ~15000-18500 cycles (~88-109 us) recurring
        roughly every 8-10 table entries, each followed by an
        anomalously short next gap (the classic signature of a single
        delayed ISR entry, not an accumulating one). The recurrence
        interval (~8 periods) matches PFM_Input's DMA capture design
        exactly: a 32-entry circular buffer with a half/full-transfer
        interrupt every 16 captured edges, i.e. every 8 periods at 2
        edges/period.

        Root cause: PFM_Input's DMA1_ChannelN_IRQn (the interrupt whose
        callback batch-processes those 16 edges, pfm_input.c) was left
        at NVIC priority 1 -- a decision inherited from the OLD, now-
        superseded per-edge interrupt-driven capture design, where
        TIMx capture interrupts genuinely needed to preempt
        HRTIM1_Master_IRQn (demoted to priority 2 on 2026-09-08) to
        avoid a real overcapture race. That reasoning stopped applying
        the moment capture became DMA-driven (2026-09-09, entry below):
        the DMA controller grabs each CCRx value in hardware with zero
        CPU/IRQ involvement, so nothing about capture fidelity depends
        on IRQ priority anymore -- only the periodic 16-edge batch-
        processing ISR still runs on the CPU, and leaving IT above
        HRTIM1_Master let its own real (non-trivial) processing time
        repeatedly steal cycles from the table-advance ISR, which is
        what a long run of identical hold entries made visible as a
        large, compounding real-time lag.

        Fix: HRTIM1_Master_IRQn restored to priority 1 (hrtim.c,
        HRTIM1_EnableMasterInterrupt()); PFM_Input's DMA1_ChannelN_IRQn
        demoted to priority 3 (pfm_input.c, PfmInput_Init()), below
        both HRTIM1_Master and the GateDriverStatus EXTI/TIMx_IRQn tier
        (priority 2). Safe because the ~8-period window before the
        circular buffer would actually wrap and lose data is orders of
        magnitude larger than HRTIM1_Master's own ISR execution time.

        stalling happened along the way, since PFM_CycleBoundaryHandler()
        only stops once g_pfmIndex reaches it -- that number alone
        can't distinguish "ran on schedule" from "was starved, then
        caught up"). Instead tracks the largest REAL TIME gap between
        two consecutive calls, using the Cortex-M4 DWT free-running
        cycle counter (170 MHz, confirmed same clock as
        HRTIM_TIMER_CLK_HZ) -- reset at every PFM_Restart(), read back
        as "OK <callCount> <maxGapCycles> <maxGapUs>".

        Result, same 100->60kHz decreasing sweep, only PFM_Input_01+02
        active (2 real channels, both genuinely wired): PFM:DIAG? ->
        "OK 200 124818 734" -- 200 calls (as expected either way), but
        a MAXIMUM GAP of 734 us between two consecutive calls. Normal
        gap at ~91-95 kHz should be ~11 us (one real period) -- 734 us
        is ~67x that. This is direct, quantitative proof that
        HRTIM1_Master_IRQHandler() (which runs PFM_CycleBoundaryHandler(),
        priority 2 -- deliberately BELOW every TIM2-5 capture channel's
        priority 1, so real edges are never missed) was starved for
        roughly 67 real periods straight, with just 2 real capture
        channels active -- not a logic bug in the table-advance code,
        and not something that requires many/floating channels to
        trigger.

        DECISION: since capture-channel interrupt load is confirmed as
        the actual mechanism, the planned fix is a DMA-based capture
        redesign -- configure each TIMx to auto-transfer its captured
        CCRx value into a RAM ring buffer via DMA on every edge, with
        ZERO CPU/ISR involvement per edge (versus one full ISR entry/
        exit + HAL dispatch + capture logic per edge today). The CPU
        would only wake up occasionally (a DMA half/full-buffer
        interrupt) to process a BATCH of already-timestamped edges,
        removing capture-channel interrupt PRIORITY/LOAD from
        competing with HRTIM1_Master almost entirely. Not yet
        implemented -- this entry documents the confirmed root cause
        and the planned direction, not a landed fix.

               (V/W) -- root cause found, real fix applied, pending

        below: a real-hardware sweep with PFM_Input_01 restricted to
        phase U (clean, 0 anomalies) alongside a full 6-channel DSLogic
        capture (U/UN/V/VN/W/WN) found V and W BOTH glitching --

        Every glitch's measured duration matched (old period + new
        period) almost exactly (ratio 0.988-1.005 across all 16
        glitches checked), on BOTH V and W -- i.e. one complete real
        SET/rising-edge event is being silently dropped, not a garbled
        or partial one.

        Found the exact documented mechanism via ST's own community
        engineering forum (search "HRTIM PWM transients greater than a
        period"): when a timer's output SET and RESET events fall
        within ~3 HRTIM clock cycles of each other, RESET always wins
        and SET is silently dropped, leaving the output low for one
        extra full cycle. U's output SET is tied to TIMPER = MASTER_PER
        (its ResetTrigger), always far from its own mid-cycle CMP1
        (duty, its ResetSource) -- no collision possible. V/W's SET is
        ALSO tied to TIMPER, but for them TIMPER = MASTER_CMP1/CMP2
        (their own ResetTrigger) -- a point that itself shifts every
        table entry as per changes (phase = k*(per+1)/N), and during a
        fast ramp can land within a few clocks of the PREVIOUS cycle's
        own CMP1 (duty) event, exactly the documented collision.

        FIX (the same one documented in that thread): V/W's output SET
        moved off the un-prioritized TIMPER event onto a dedicated
        CMP3 compare (HRTIM's collision rule favors the higher-numbered
        compare register, so SET now wins ties against RESET's CMP1
        instead of losing). CMP3xR set once at init to a small fixed
        16-tick offset (not duty-dependent, no per-cycle updates
        needed) -- negligible against real period lengths (1200+
        ticks). Deliberately narrow: only channels 1..HRTIM_NUM_
        CHANNELS-1 change; channel 0 and the unused channels beyond
        HRTIM_NUM_CHANNELS (free-running, no MASTER_CMPk race possible)
        keep SetSource = TIMPER.

        Rebuilt clean (zero warnings, text 47140 -> 47252 bytes).

2026-09-04  —  Masked interrupts during the settling wait's critical section
---------------------------------------------------------------------------
  Change:  Second follow-up to the cold-start phase-lock fix. A fresh
        DSLogic capture after the loop-tightening entry directly below
        showed real improvement (first pulse 200 ns -> 600 ns; U/V/W
        edge-timing error ~700 ns -> ~230-270 ns off target) but a
        genuine, non-shrinking residual remained -- and it varied run
        to run (200 ns, then 600 ns), which pointed away from a fixed
        software-latency floor and toward interrupt preemption:
        HRTIM1_PWM_Start()'s poll runs with global interrupts enabled,
        and SysTick (priority 0, the HIGHEST in this firmware -- see
        FixSysTickPriority()) or USART2 (priority 2, this very FIRE
        command's own reply path) can legitimately preempt the tight
        poll loop for a handful of cycles at exactly the wrong moment.

        ~385 us for a uint16_t `per`'s longest representable period,
        typically ~10 us at 100 kHz). Since HAL_GetTick() can't advance
        while global interrupts are masked (it's SysTick-driven, and
        SysTick is masked too), the previous entry's wall-clock timeout
        doesn't work here -- replaced with a plain 1,000,000-iteration
        spin-count ceiling, deliberately loose (many milliseconds of
        real time even pessimistically) rather than tuned, so it can
        only ever trip on a genuine hang, never in normal operation.

        re-uploaded, FIRE -> OK repeatedly (fired twice back to back),
        board stayed fully responsive to *IDN?/TABLE? throughout -- no
        hang, and no UART data loss from the masked window (a ~10 us,
        worst-case ~385 us mask is far shorter than the ~1 ms/byte
        margin at 9600 baud, so an in-flight RX byte just sits in the
        UART's hardware data register a little longer, unaffected).
        Re-capturing with DSLogic to confirm the residual actually
        shrank is the next step, not yet done as of this writing.

2026-09-04  —  Bugfix: cold-start phase-lock glitch on every FIRE
------------------------------------------------------------------

        archive's raw bit-packed channel data). Symptom: on every
        `FIRE`, U/V/W's first-ever output edges all landed on the

        intended -- producing ~1-2 garbled cycles (one phase measured
        holding ON ~7.4x too long; that first "period" reading as low

        what the user had independently noticed as "~60 kHz garbage for
        the first ~2 periods" on a real scope.

        Root cause: HRTIM1_PWM_Start()'s HAL_HRTIM_WaveformSetOutputLevel()
        calls (needed, per ST's own HAL guidance, to avoid an undefined
        complementary-pair state when DeadTimeInsertion is enabled)
        force TA1/TB1/TC1 all ACTIVE at the same instant, with no
        regard for their intended stagger. Timer A's ResetTrigger
        (MASTER_PER) happens to coincide with its own natural period
        rollover, but Timers B/C (ResetTrigger = MASTER_CMP1/CMP2)
        aren't genuinely phase-locked until they've received their
        first Master-CMPx-triggered reset -- which hasn't happened yet
        at the moment the counters first start.

        Fix: HRTIM1_PWM_Start() now starts the counters as before, but
        delays connecting the outputs to the pins (WaveformOutputStart())
        until the Master's own MREP (repetition) flag confirms one full
        period has genuinely elapsed in hardware -- by then every
        timer has already received its first phase-defining reset, so
        the first VISIBLE edge is already correctly phase-locked.
        Waiting on the hardware flag rather than computing a busy-wait
        from `per`/HRTIM_TIMER_CLK_HZ makes this automatically correct
        for whatever period is currently loaded -- no hardcoded 100 kHz
        assumption, so it stays correct if/when variable-frequency
        tables exist (per user request, 2026-09-04). HRTIM_MASTER_IT_MREP
        (armed at boot by HRTIM1_EnableMasterInterrupt(), and still
        armed from any previous shot) is masked for the duration of
        this wait and any stale flag discarded first -- otherwise
        PFM_CycleBoundaryHandler() would fire for real during the
        settling wait and silently advance the table to step 1 before
        step 0 was ever visible on the pins. Bounded to 5 ms
        (>12x margin over the ~385 us worst-case period a uint16_t
        `per` can represent) with an Error_Handler() fallback, matching
        this file's existing defensive-timeout convention (see
        HAL_HRTIM_PollForDLLCalibration() in HRTIM1_FullInit()).

        Verified: full clean rebuild (make clean && make all -j4, zero
        warnings; text grew 88 bytes). Verified on real hardware:
        reflashed over serial, re-uploaded a 500-entry table, sent
        FIRE -> OK promptly (no hang from the new bounded poll -- the
        real risk this change introduced), board stayed responsive to

        `while time.time() < deadline: chunk = ser.read(128)` poll
        loop against a Serial(..., timeout=1.0) port. pyserial's
        read(size) keeps trying to fill the *entire* requested size
        until the port's own timeout elapses, even once a short reply
        (every firmware reply here is a handful of bytes, e.g.
        "OK\r\n") has already fully arrived -- so every single
        TABLE:STEP round-trip was costing close to the full 1 s
        timeout instead of the real ~20-30 ms wire time at 9600 baud.
        500 entries were taking 8+ minutes; this was mistakable for
        "9600 baud is just slow", but the baud rate was never the
        problem.

        Fix: replaced the poll loop with ser.read_until(b"\n"), which
        returns the instant the terminator arrives (falling back to
        the port's timeout only on a genuine no-reply failure, which
        still needs to time out and raise). No protocol or firmware
        change. Verified: a real 500-entry upload (profile 1) dropped
        from 500-1000+ s to 20.2 s measured wall-clock, same successful
        `TABLE:END -> OK 500` result.

        Considered and deferred (see the FIRE entry below's own
        real-hardware pass for why 20 s was accepted as fine for now):
        batching multiple TABLE:STEP entries per line (needs a
        firmware/protocol change; marginal win once the read-loop bug
        is fixed, since ~30 s of raw payload at 9600 baud is close to
        the real floor for 500 entries either way) and pipelining
        without waiting for each ACK (real risk of silently overrunning
        uart.c's single-line RX buffer without first checking its
        buffering model -- not done without that check).

2026-08-31  —  Bugfix: ROM bootloader Go-jump left interrupts dead
---------------------------------------------------------------------
  Change:  Found and fixed on real hardware while first testing
        wham_serial_flash.py end-to-end. Root cause, symptom, and fix
        are documented in full in boot_jump.c's BootJump_CheckAndEnter()
        and in docs/serial_reflash_guide.md Section 4 -- summary:

        Symptom: a serial reflash reported success (write + verify both
        passed via stm32flash), but the newly-flashed firmware was
        completely unresponsive over USART2 afterward -- *IDN? got no
        reply -- until the board was power-cycled, at which point it
        worked immediately and correctly.

        Root cause: stm32flash's -g (the ROM bootloader's "Go" command)
        branches to the new app without performing a real chip reset.
        SCB->VTOR and SYSCFG->MEMRMP, left pointing at the ROM
        bootloader's own vector table from the *previous* boot's jump
        INTO the bootloader (the normal BOOT-command flow), are never
        corrected by anything in this firmware -- system_stm32g4xx.c's
        SystemInit() only sets VTOR under USER_VECT_TAB_ADDRESS, which
        is not defined here (the CubeMX default). Every interrupt,
        including the USART2 RX interrupt the whole command parser
        depends on, vectored into the ROM bootloader's table instead of
        the app's own.

        Fix: BootJump_CheckAndEnter()'s normal-boot path now
        unconditionally restores SCB->VTOR = FLASH_BASE and the main-
        Flash SYSCFG remap before falling through to HAL_Init(). No-op
        on a true reset (both already correct there); the actual fix on
        the Go-jump path.

        Verified: flashed a new firmware version over serial, queried
        *IDN? immediately with no manual reset, got the new version back
        correctly -- confirmed twice in a row (v0.5, then v0.6).

        Not yet ported to the sibling PFM-STM32G474/-V4 projects, which
        carry the same unfixed boot_jump.c this one was forked from --
        deliberately deferred per project decision, not forgotten.

2026-08-31  —  SCPI-style hierarchical command dispatch
-------------------------------------------------------------
  Change:  Replaced cmd_parser.c's flat case-sensitive exact-match table
        with SCPI-style matching (scpi_match()/scpi_token_match()):
        colon-separated hierarchy levels, per-level short/long form
        (mandatory-uppercase-prefix + optional-lowercase-suffix),
        case-insensitive, exact query-suffix (?) matching, tolerant of
        a leading colon on input. Table stays flat (one row per leaf
        command, full mnemonic path as the pattern) -- no separate tree
        structure to build or maintain.

        Verified with a standalone native (non-cross-compiled) test
        harness before wiring in: 19 cases covering short/long form,
        mixed-form, wrong depth, wrong query suffix, case variants, and
        leading-colon tolerance, all passing. Also confirmed strtok_r/
        strncasecmp/isupper actually link under this toolchain's
        --specs=nano.specs (not guaranteed in every newlib-nano config).

        *IDN was renamed to *IDN? to match real IEEE 488.2/SCPI form,
        now that the trailing ? is meaningfully enforced.
